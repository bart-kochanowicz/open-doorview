# Known limits and open questions

Read this before trusting any part of the project.

## Scope of the evidence

- **One camera.** Everything was developed and tested on a single RH-PD10. Another unit, batch or firmware revision may differ (the board, the MCU firmware, the flash layout).
- **Days, not months.** The interrupt-driven driver ran 8 hours without a stall once, but the overnight run of 2026-11-22 showed **three data-path stalls in 11.5 hours** (after 8 h, 63 min and 3.5 h; see [the stalls](wifi-companion.md#the-data-path-stalls-of-2026-11-22)). The camera recovered each time by restarting after about 10 minutes (Majestic's watchdog); the cause of the stall is unknown. Rare failures cannot be excluded.
- **The shipped `doorview-mqtt` was rebuilt four times on 2026-11-20 and 2026-11-21.** The first rebuild (after code review: SIGPIPE handling and a receive-buffer fix, hash `d628a47c…`) ran on the camera for minutes and two reboots. The second build added the motion sensor and a keepalive fix (hash `cadd0d5c…`); it ran from RAM first and was then installed with stage 3 on the same day. The third build added the optional snapshot (hash `3a52f28e…`); the fourth (`a8c3b8c0…`, 2026-11-21) raises the picture limit to 320 KB for 1080p stills. Later builds added the motion rate threshold (`5d373cf7…`), the live view and, on 2026-11-22, `motion_settle` and `wifi_reboot` (`66a866b4…`, the one installed now). Observed with the second build after its install and again after a reboot: the Motion entity went ON in Home Assistant when a hand was waved in front of the lens. Still only minutes to hours of runtime; not observed with this build: a long run, a broker outage on the camera. The SIGPIPE, receive-buffer and keepalive paths were exercised by the Docker suite (including an ASan/UBSan build) and under `qemu-user`.
- **Stage 1 and 3 installers are new.** The stage 1 installer was written for this repository and has been tested only on fixture trees (the unit received its stage 1 files through earlier scripts that did not survive in this form). The stage 3 installer was run on the unit on 2026-11-20 (install, `rollback.sh`, install again; the rollback restored the previous driver exactly). The stage 1 installer has still not run on a camera. Stage 2's payload was installed and verified on the unit; its installer script was hardened after review and has been run only by the fixture tests.
- **No restore of the factory firmware has ever been tested.** Two identical reads prove consistency, not that writing them back works.

## Things that are guesses

- The battery capacity scale. The coprocessor log suggests a percentage computed from the battery voltage (raw 458 empty, 475 low, 558 full; see [the factory firmware](factory-firmware.md#battery-scale-from-the-coprocessor-log)). On 2026-11-22 the value fell from 100 to 51 in 8 h 50 min on battery, read 13 for one minute with the screen on and 88 on the charger; so a reading under load or while charging is not the charge state. After the last reboot (2026-11-20) the MCU reported `status=1, usb=0, capacity=100` (on battery) in every PowerInfo frame for at least 3 minutes while the camera was connected to USB (confirmed by the owner); in earlier boots the frames showed `status=2, usb=1`. The cause is unknown, so Home Assistant's External power can be wrong for a while after a boot.
- The meaning of power status 2 (charging versus full).
- The panel controller and FPC pinout.
- That the Hi3861 identification of the coprocessor is exact.
- The cause of the early-boot resets. On 2026-11-20 **every one of three software reboots** (`reboot`) showed two resets before the third attempt reached the login prompt (three "System startup" banners, one "Welcome to OpenIPC" per capture; the resets come after "Starting mdev..." or earlier and before any Doorview hook). Whether a cold start (power removed) behaves the same was not tested. The camera was on a USB supply (ISDT Power 200H) throughout. **Observed again on 2026-11-23 with a timestamped UART capture** (one software reboot, on USB power): the first boot reset itself 3 s after "Starting mdev..." (about 10 s after the kernel started); the second reached U-Boot, which printed `Bootlimit (2) exceeded. Using altbootcmd.` and `Boot limit exceeded -- entering FAILSAFE (network + SSH only)`, and then sat there for 71 s until the coprocessor reset the SoC (the "mcu check soc alive" guard, assumed from the 70 s of the factory log); the third boot reached the login prompt. So the second reset is U-Boot's boot counter, not a fault of its own; what makes the first boot reset is still unknown (it falls in the Doorview module phase). The software reboot cost 85 s this way.
- Boot time of a clean boot, measured on 2026-11-23 from two timestamped UART captures of software reboots, with the broker's log (UTC, whole seconds, the host clock set the camera's time of reboot) for the last step. Seconds after the final U-Boot banner: kernel starts at 3.6 (a 1 s autoboot delay, a USB scan and a flash scan; one capture also showed the boot-limit notice), the root file system is mounted at 6.6 (the ethernet MAC driver waits 0.9 s for a PHY that is not there), the Wi-Fi station request is queued at 9.9, Majestic starts at 11.4 and **the camera connects to the broker 0.25 s after that, 11.6 s after the reset**; the Wi-Fi association and DHCP took about 1.7 s. The user-space scripts from the root mount to Majestic take about 4.7 s (seeding 0.9, fake-hwclock 0.5, mdev 1.2, network 1.2, vendor modules 1.1). The factory firmware asks the coprocessor for the wake-up reason 0.44 s after power-on. (An earlier version of this entry put the network at about 15 s; that came from a first capture in which the two early-boot resets were still part of the interval.) The first boot after a software reboot reset itself again in the second capture, 3.2 s after "Starting mdev..." and about 7 s after the kernel started, both times; a hardware watchdog left armed by the previous run is a hypothesis only.
- The PIR sensor works, but is not used yet. It belongs to the coprocessor. **Observed on 2026-11-23** (one unit, indoors, a hand waved at the lens, from a test build of the network driver run from RAM, see below): `8a:78 01 00` switched it on and every wave produced `0x03` alarm frames, `01` at the start and `00` at the end of a movement (five pairs for five waves); `8a:78 00 00` switched it off and nothing arrived in the next 50 s of waving. The coprocessor sent no answer to either command that the driver logs. A sensitivity command `8a:79` (level 1) was also sent; its effect is unknown. One alarm arrived before the switch-on command had been sent (after the sensitivity command), so the PIR may have been on from the start or switched on by that command; the factory log said `isEnablePir:0`. Detection distance, field of view, the time from movement to the frame, the cool-down between alarms and false alarms are not measured. The unit was left with the PIR off. **Standby (2026-11-23):** the factory sequence (`8a:77 07`, `9a:03`, `8a:61 01` on `0xa0`) switched the SoC off and the power button woke it (details in [factory firmware](factory-firmware.md)); the wake-ups by PIR, key and timer are untested because they need the changed `syslink_poll`, which is not installed. The sleep ran from a test driver loaded into RAM, so nothing sleeps by itself yet. **Update (2026-11-23, later):** stage 4 is installed on the camera (the two drivers replaced; nothing starts by itself). After `echo 780100` (PIR on) and the standby, the camera woke by itself when a hand was waved in front of the lens: the coprocessor reported `pir`, the new `syslink_poll` accepted it (`wakeup reason=pir`), and the camera was on the broker 11.6 s after the U-Boot banner. After the earlier wake by the power button (`poweron`) it took 33 s, because the Wi-Fi association had to be made again; why the PIR wake did not need that (a shorter sleep, about 50 s against about 2 min, or the reason) is not known. Wake-ups by the key and the timer are untested. **Observed on 2026-11-23 with the daemon's sleep running:** the camera was woken three times with the reason `timer`, each exactly 5 minutes after it went to sleep (13:11, 13:17 and 13:24 UTC), so the coprocessor has a default wake-up timer that we never switched off. With about 12 s of boot and 60 s of idle time that is more than a fifth of the time awake. Stage 6 sends the wake-up timer command `8a:7b` (0 = off, from the factory firmware: an assumption until it is seen to work) before every sleep. **Stage 5 and 6 (the sleep logic of the daemon, `sleep_after`, and the wake-up timer command), observed on 2026-11-23 on the camera on USB power with `sleep_after=60`, `sleep_usb=1` and `snapshot_delay_ms=1500`:** after a wake-up by the PIR the daemon reported motion `ON` with one snapshot 12 s after the U-Boot banner and the camera went to sleep again about 70 s later; the unattended cycle ran several times, each time with a clean disconnect (`availability` offline) before the power was cut. **The default 5-minute wake-ups by the coprocessor's timer stopped once the daemon sent `8a:7b` with 0 before the sleep:** the camera slept for more than 9 minutes without waking (before: every 5 minutes, three times in a row). **2026-11-23, after the video motion detector was switched off and the PIR became the only source:** the owner reported that the PIR woke the camera only when a hand was held about 5 cm from the lens; the corridor in front of the door is about 2 m wide, so a visitor is never farther away. The sensitivity of the PIR (the coprocessor setting `8a:79`; one value, level 1, was sent by mistake on 2026-11-23, so the factory value may have been changed) is therefore too low and is being tuned. **Boot time (measured on the unit, 2026-11-23):** U-Boot banner to Majestic 11.4 s at the start of the day, 8.9 s with stage 8, 7.9 s with `bootdelay` 0, **7.0 s with stage 9 and `quiet`**; to the broker 7.8 s. **From the U-Boot banner of a PIR wake-up to the person alert in Home Assistant: 13.9 s** (motion 9.0 s, picture 12.5 s, person 13.9 s), against about 20 s in the morning; **later the same day 11.8 s** with stage 10 and the ethernet driver left out (broker 5.6 s, motion 5.6 s, Majestic 6.05 s, picture 10.2 s, person 11.8 s; the kernel phase 3.0 s instead of 3.9 s), and the person check on the server answers a clear person in 0.2 s instead of about 1.1 s (two detectors, see the homelab). What is left is mostly fixed: U-Boot 1.6 s (USB scan and flash layout detection are in the bootloader), about 1 s between U-Boot and the kernel's first clock tick, about 0.9 s of OpenIPC's `/init` (flash checks and the JFFS2 overlay mount; it runs from the read-only root file system), the vendor modules about 1.2 s, and Majestic about 3 s from its start to the first picture at a cold start (1.33 s at a warm restart; resolution, slow shutter and frame rate change that by at most 0.12 s); the picture is now 1280 × 720 at quality 55 (about 77 KB, 1.9 s over the Wi-Fi) taken 700 ms after the motion, and Home Assistant waits for it in tenths of a second. The vendor video modules (1.7 s; the audio modules are only 0.2 s and are not needed) are now the longest step in Linux; the USB scan and the flash layout detection in U-Boot (about 0.6 s) are in the bootloader itself, not in its environment. **U-Boot `bootdelay` was set from 1 to 0 on 2026-11-23** with `fw_setenv bootdelay 0` after two identical reads of the 64 KB environment partition (`/dev/mtd1ro`); only that variable changed. It is no longer possible to stop the autoboot on the UART; recovery is the SPI programmer, the failsafe boot after two failed starts, and `fw_setenv bootdelay 1` from the running system. **Overlay clean-up (2026-11-23):** the old `*.previous`, `*.before-sleep` and `*.before-timer` backups were deleted (the binaries rebuild bit for bit from the repository, and the overlay was backed up twice before every stage) and `/root/.ash_history` (247 KB, rewritten at the end of every UART session, so flash wear) was replaced by a link to `/dev/null`. With the PIR at sensitivity level 3 (`8a:79`) a person about 1 m away was seen; at the lowest level only a hand 5 cm from the lens was. The wake-up by the person (a visitor in front of the peephole) and a day of battery use are not measured yet. A front-button press that wakes the camera is consumed by the coprocessor, so it does not start the LCD preview; the entities are unavailable while the camera sleeps. The test driver is `syslink_net_irq.ko` with the `mcu` parameter (source in the repository, binary not shipped).

## Not implemented

- Snapshot: the daemon with `snapshot=1` is installed persistently (stage 3). The current build (hash `a8c3b8c0…`, reproducible) was installed on 2026-11-21 together with `video0.size: 1920x1080` in `/etc/majestic.yaml` (two identical overlay reads before each write; it ran from RAM first). **Observed on the unit:** pictures of 1920 × 1080, 135 to 168 KB, published in 3.9 to 4.9 s each; four of them reached the Home Assistant archive intact; the owner reported the LCD preview working and a phone notification with the picture after the change. The first persistent build (`3a52f28e…`, 480 × 270 pictures, about 12 KB) had produced a phone notification on 2026-11-20 (reported by the owner). Observed later the same day: a software reboot with this build brought everything back without a power cycle: the web and console accepted the new root password, Majestic still ran at 1920 × 1080, the daemon connected after three `broker unreachable` attempts, the LCD service started and the Wi-Fi driver reported `errors=0`; the boot log again showed two early resets before the successful start. Three waves of a hand produced three pictures on the camera and, according to the owner, two phone notifications (the second wave inside Home Assistant's one-minute window was silenced); the automation traces were not read. A picture of 171 to 178 KB took up to 6.4 s to send, which the old whole-send limit of 5 s would have cut. **Not observed:** a long run at 1080p, live RTSP video at 1080p (expected not to play in real time), the false-alarm rate, and a snapshot after that reboot. The send of a large picture blocks the daemon's loop for up to about 5 s. The broker's camera ACL has no `homeassistant/image/…` line, so the image discovery message is dropped there; Home Assistant declares the `image` entity by hand.
- Live view (`live=1`, a slide show on demand through the broker): installed on 2026-11-22 with build `66a866b4…` (reproducible). **Observed on the unit:** started from the "Door events" panel of Home Assistant (phone app), three views of 13, 11 and 34 pictures in 6.7, 5.6 and 18.4 s: about 10.5 to 11.6 KB per picture (640 by 360), 1.9 pictures per second, 19 to 23 KB/s over the link. Not measured: a full 30 s view, a view while a night snapshot is sent, and a view during a Wi-Fi stall.
- `wifi_reboot=90` and `motion_settle=60` are in `mqtt.conf` of the unit (2026-11-22, build `66a866b4…`). **Observed on the unit:** the daemon's restart works (a test run with a frozen counter file restarted the camera, which came back with the daemon connected; about 85 s pass between the `reboot` call and the new boot). **Not observed:** a real stall ended by the daemon, and whether `motion_settle=60` removes the false motion after a restart in the dark (a restart in daylight showed a counter at 0 for 71 s).
- Motion detection: the motion sensor is installed (daemon with `motion=1`, `motionDetect` enabled in `/etc/majestic.yaml`) and was seen to work after install and after a reboot, in hand-waving tests only. The false-alarm rate (shadows, light changes, the corridor), sensitivity, region of interest and night behaviour were never examined. Person detection does not exist.
- **The camera's web interface is an administrator interface.** One account (root), no roles, a web terminal, configuration API, firmware update and factory reset, over HTTP in clear text; RTSP and SSH use the same root password. Anyone who can reach port 80 and knows the password has a root shell. Keep the camera's VLAN closed to everything except what needs it, use a long unique root password (the OpenIPC default is `12345`), and do not give Home Assistant or anything else a credential for it. The snapshot feature exists so that nothing has to.
- A default route: stages 1 and 2 set only the on-link route, so the camera cannot reach another subnet (observed 2026-11-20: `nc` to a broker in another subnet failed with "Network unreachable" and succeeded after `ip route add default via <router>` in RAM). Stage 3 adds it from `gateway=` in `mqtt.conf`. The first on-camera boot of that path failed: BusyBox `ip route show default` prints the whole routing table, so the first version of `S97doorview-mqtt` concluded a default route existed. It was fixed (it now looks for a `default` line) and the tests' `ip` stand-in now behaves like BusyBox; the fixed hook then added `default via <router>` by itself on the next boot (observed 2026-11-20).
- DHCP, automatic Wi-Fi reconnect (an optional watchdog exists, off, and its recovery step is unproven), WPA3, open networks, 5 GHz, SSIDs or passphrases over 31 bytes.
- Signal strength and access-point information (the factory command exists; it was never sent because commands to the MCU are risky).
- TLS for MQTT.
- Battery life: about 15 to 18 hours on battery (2026-11-22), against weeks with the factory firmware, which switches the SoC off between events. Sleep is not implemented; the commands are in [the factory firmware](factory-firmware.md#the-factory-power-cycle-from-the-factory-firmware).
- Audio, the speaker and microphone, the PIR, the battery fuel gauge beyond the MCU's value. The IR-cut filter and IR LEDs work through Majestic's `nightMode` with GPIO 8 (see [night vision](night-vision.md)); motion detection in the dark works in night mode (IR LEDs on; rate threshold `motion_min_rate=20`) but the camera does not switch to night mode by itself in a dim room, where the noise is above the threshold; see the measurements there and the night snapshot path was not confirmed end to end.
- Person detection. The factory firmware ran HiSilicon's `hi_ivp` detector on the camera after a PIR wake-up; OpenIPC has no such library. Under Linux the SoC has one core, about 27 MB of RAM and no neural accelerator, so classification runs elsewhere with the camera only triggering and sending a frame. **Observed (2026-11-23, one homelab):** a detector container (Faster R-CNN, COCO classes) beside Home Assistant classifies each archived snapshot in 1 to 2 s on the CPU and flags a person at 50 % confidence or more; on the 190 archived pictures it gave 99.6 % for the one picture of a person close to the lens after the camera was mounted, and below 40 % for an empty corridor at night. The sample is small (one real positive since mounting), so the recall for a person at the door, in the dark or far from the lens is not measured. It adds a second notification step only; the first notification is still sent for every motion.
- Over-the-air update, and anything that survives a re-flash.

## Gaps in what is recorded

- **The first OpenIPC flash.** The repository does not record the command sequence used. See [openipc-flash.md](openipc-flash.md).
- **`syslink_bg.ko`.** The binary on the unit (SHA-256 `a21e588b...`, 6,048 bytes) was built from an earlier revision of `syslink_bg.c` that was not kept. The source in `firmware/kernel/syslink-handshake/` is the later revision, which adds a `resume_connected` parameter and builds to a different file (`9a0567e0...`). The shipped binary is the one that ran for days; the later source has only been run from RAM. Consequence: the fallback in `S41doorview-network` that restores the heartbeat driver passes `resume_connected=1`, which the shipped (older) binary does not accept, so **that last-resort fallback would fail to load** on a unit with the shipped binary. It only matters when both network drivers fail to start.
- **`button-preview`, `vo-live-30`, `libuclibc-compat.so`.** Rebuilds are not bit-identical to the tested binaries; see [building.md](building.md).
- **Wi-Fi from a cold neighbour cache** with a second client was not retested systematically after the interrupt driver was introduced.

## Third-party material

- `vo.ko` is a proprietary vendor module from OpenIPC's firmware repository. It is downloaded, never redistributed here.

- The kernel modules declare `MODULE_LICENSE("GPL")`.
- This repository has **no licence file yet.** Add one before publishing (the kernel modules need to remain GPL-compatible).
